# Site Infrastructure

Kubernetes cluster on OpenStack (Metacentrum MetaVO / e-INFRA CZ) using Terraform + Ansible + ArgoCD (GitOps).

## Stack

| Layer | Technology |
|-------|-----------|
| Infrastructure | OpenStack (Metacentrum MetaVO, Brno) |
| Provisioning | Terraform |
| Configuration | Ansible |
| Kubernetes | RKE2 (3-node HA control plane) |
| GitOps | ArgoCD |
| Ingress | Traefik v3 (Gateway API, DaemonSet on CPs) |
| Load Balancer | OpenStack Octavia (API LB + Ingress LB) |
| TLS | cert-manager + Let's Encrypt HTTP-01 |
| Storage | Longhorn (LVM over Cinder volumes) |
| Registry | Harbor (container image registry) |
| Secrets | HashiCorp Vault + External Secrets Operator |
| Database | CloudNativePG (PostgreSQL operator) |
| Identity | Keycloak (Keycloak Operator) |
| Monitoring | kube-prometheus-stack (Prometheus + Grafana + Alertmanager) |

## Prerequisites

- Terraform >= 1.11
- Ansible >= 2.16
- Helm >= 3.0 — required by the `kubernetes.core.helm` module, must be in `PATH` on the machine running the playbook
- `clouds.yaml` at `terraform/infra/clouds.yaml` (gitignored) — OpenStack application credentials
- GCS credentials for Terraform state — authenticate with:
  ```bash
  gcloud auth application-default login
  ```

Install Python dependencies:
```bash
pip install -r requirements.txt
```

Install Ansible collections:
```bash
ansible-galaxy collection install -r ansible/requirements.yml
```

## Deployment

Full deployment requires **four steps**. Steps 1–2 and step 4 are fully automated. Step 3 is a one-time manual Vault initialization that cannot be automated by design.

```
terraform/infra  →  ansible  →  vault operator init  →  terraform/vault
     (1)              (2)               (3)                    (4)
                                                         [everything auto from here]
```

### 1. Infrastructure — Terraform (infra)

Provisions all OpenStack resources (network, instances, volumes, load balancers, floating IPs) and GCP KMS resources for Vault auto-unseal. Renders the Ansible inventory and writes the GCP SA key to `ansible/files/vault/kms-sa-key.json`.

```bash
cd terraform/infra
terraform init
terraform apply
```

`terraform apply` automatically writes two files:
- `ansible/inventory/host_vars/cp-0.yml` — cp-0 floating IP (gitignored)
- `ansible/inventory/group_vars/all/terraform.yml` — API LB floating IP for kubeconfig + TLS SANs

Update DNS A records before continuing:
```bash
terraform output ingress_lb_public_ip
# → point all hostnames to this IP
```

### 2. Cluster provisioning — Ansible

Sets up all nodes, installs RKE2, bootstraps ArgoCD, and applies the root ArgoCD Application. From this point ArgoCD takes over and syncs all components.

```bash
cd ansible
ansible-playbook site.yml
```

Available tags to run individual plays:

| Tag | What it runs |
|-----|-------------|
| `--tags system` | Timezone, NTP, users, SSH keys, LVM disk setup, open-iscsi |
| `--tags rke2` | RKE2 HA control plane (init + join) + RKE2 agents on workers |
| `--tags argocd` | Gateway API CRDs + ArgoCD Helm install |
| `--tags argocd,apps` | All of the above + apply secrets, ArgoCD projects, and root Application |

The full playbook in order:

| Play | Hosts | Description |
|------|-------|-------------|
| 1 — System setup | `rke2_cluster` (all nodes) | OS configuration, disk setup |
| 2 — Install RKE2 | `rke2_cluster` (all nodes) | Role dispatches init/join/worker by group; fetches `artifacts/kubeconfig` from cp-0 |
| 3 — Bootstrap ArgoCD | `localhost` | Installs Gateway API CRDs and ArgoCD via Helm |
| 4 — Deploy ArgoCD applications | `localhost` | Creates namespaces, applies bootstrap secrets, ArgoCD AppProjects, and root Application |

> **Note**: Only cp-0 has a floating IP. Ansible reaches cp-1, cp-2, and workers via SSH ProxyJump through cp-0. Plays 3 and 4 run entirely from localhost using `ansible/artifacts/kubeconfig`.

> **RKE2 join ordering**: cp-1, cp-2, and all workers wait for port 9345 on the LB VIP before joining, so all nodes can start in parallel — ordering is self-enforced by the role.

### 3. Vault initialization (one-time manual step)

Wait for ArgoCD to deploy Vault (check `kubectl get pods -n vault`), then initialize it:

```bash
kubectl exec -n vault vault-helm-0 -- vault operator init
```

Save the **recovery keys** and **root token** in a password manager. Vault will auto-unseal on every restart via GCP KMS — recovery keys are only needed if the KMS key is ever lost or revoked.

### 4. Vault provisioning — Terraform (vault)

Configures the KV v2 secrets engine, stores service credentials, and sets up the Kubernetes auth backend for External Secrets Operator.

```bash
cd terraform/vault
cp terraform.tfvars.example terraform.tfvars
# Fill in vault_root_token and all service credentials
terraform init
terraform apply
```

After this step ESO connects to Vault automatically and syncs all credentials into Kubernetes Secrets. No further manual steps are needed — the cluster is fully operational.

### GitOps — ArgoCD sync waves

ArgoCD deploys all components in sync waves — wave N must be healthy before wave N+1 starts.

| Wave | Applications | Why this wave |
|------|-------------|---------------|
| 1 | `traefik`, `cert-manager`, `longhorn`, `harbor`, `vault`, `cnpg`, `kube-prometheus-stack`, `keycloak-operator`, `eso` (Helm charts + operators) | Core infrastructure — must be running before anything depends on them |
| 2 | `traefik-config` (Gateway + GatewayClass), `cert-manager-config` (ClusterIssuers), `keycloak-postgres` (CNPG Cluster), `eso-config` (ClusterSecretStore) | Requires wave 1: Gateway needs Traefik, ClusterIssuers need cert-manager, ESO config needs ESO CRDs |
| 3 | `longhorn-config`, `argocd-config`, `harbor-config`, `vault-config`, `keycloak-config`, `grafana-config` | Requires wave 2: HTTPRoutes need the Gateway, Keycloak needs its database, ExternalSecrets need the ClusterSecretStore |

Monitor sync status:
```bash
export KUBECONFIG=ansible/artifacts/kubeconfig
kubectl -n argocd get applications
```

## Secrets management

All service credentials are stored in **HashiCorp Vault** (KV v2, path `secret/`) and synced into Kubernetes Secrets by **External Secrets Operator** using Vault's Kubernetes auth — no static tokens required.

| Vault path | Kubernetes Secret | Namespace | Used by |
|------------|-------------------|-----------|---------|
| `secret/grafana` | `grafana-credentials` | `monitoring` | kube-prometheus-stack |
| `secret/keycloak` | `keycloak-credentials` | `keycloak` | Keycloak Operator bootstrap admin |
| `secret/harbor` | `harbor-credentials` | `harbor` | Harbor admin password |

Credentials are provisioned into Vault by `terraform/vault/01-vault.tf` and synced to K8s via `ExternalSecret` resources in each app's `config/` directory.

## TLS certificates

Three issuers are available in `argocd/apps/cert-manager/config/`:

| Issuer | Use case |
|--------|---------|
| `letsencrypt-staging` | Testing — untrusted CA, no rate limits |
| `letsencrypt-prod` | Production — trusted, rate limited |
| `selfsigned-ca` | Offline / dev — import `selfsigned-ca-tls` secret as trusted CA |

**Always test with `letsencrypt-staging` first.** If issuance succeeds (browser warning is expected), DNS and port 80 routing are confirmed working. Then switch to `letsencrypt-prod`. Production is rate-limited to 50 certificates per domain per week ([Let's Encrypt rate limits](https://letsencrypt.org/docs/rate-limits/)).

cert-manager uses **HTTP-01 challenge** — port 80 must be reachable from the internet during issuance. Renewals are automatic.

## Adding a new subdomain

1. Add a DNS A record → Ingress LB floating IP
2. Add an HTTPS listener in `argocd/apps/traefik/config/traefik-gateway-Gateway.yaml`
3. Add a `Certificate` in `argocd/apps/cert-manager/config/<name>-tls-Certificate.yaml`
4. Add an `HTTPRoute` in your application's `argocd/apps/<app>/config/<app>-HTTPRoute.yaml`
5. Push to `kost` branch — ArgoCD applies automatically

## HashiCorp Vault

UI: `https://vault.ass-nss.jkuzel02.online`

Standalone mode (single pod, file storage on Longhorn). TLS terminated at Traefik. Auto-unseal via **GCP KMS** (`enc-ass-nss-project` / `vault-keyring` / `vault-unseal-key`) — fully automatic on every pod restart.

> **DR note**: Vault data lives on a Longhorn PVC. Back up via Longhorn snapshots to S3. The GCP KMS key ring is permanent (cannot be deleted from GCP) — on a full cluster rebuild, import it back into Terraform state and Vault will auto-unseal against the same key.

```bash

  --docker-server=harbor.ass-nss.jkuzel02.online \

  --docker-password=<password> \
```
